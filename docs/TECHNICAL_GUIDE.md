through the code, and how the pieces talk to each other. Read it alongside the source code:
every Java file also has comments.

> The app runs on your PC with Maven, uses your **local PostgreSQL**, and Kafka runs in a
> single Docker container. Stage 2 (everything in Docker) and Stage 3 (AWS EC2) come later.

## 1. What the app does

A small REST API to **create, read, update and delete (CRUD)** students.

| Method | URL                   | What happens                         | Success code   |
|--------|-----------------------|--------------------------------------|----------------|
| POST   | `/api/students`       | Insert row **+ publish Kafka event** | 201 Created    |
| GET    | `/api/students`       | List all students                    | 200 OK         |
| GET    | `/api/students/{id}`  | Get one student (404 if missing)     | 200 OK         |
| PUT    | `/api/students/{id}`  | Update name, email, course           | 200 OK         |
| DELETE | `/api/students/{id}`  | Delete the row                       | 204 No Content |

**Data model:** one table, `students`:

| Column | Type         | Rules                          |
|--------|--------------|--------------------------------|
| id     | bigint       | Primary key, generated by DB   |
| name   | varchar(255) | Required                       |
| email  | varchar(255) | Required, valid email, unique  |
| course | varchar(255) | Optional                       |

**The extra twist:** whenever a student is created, the app sends a `STUDENT_CREATED`
message to Kafka. A Kafka consumer inside the same app reads it and logs it. In a real
company, that consumer would be a separate "email service" sending a welcome email.

## 3. The layered design

The code is split into layers. Each layer has **one job** and only talks to the layer below it.

```
 HTTP request
     │
     ▼
┌───────────────┐  Knows about HTTP: URLs, JSON, status codes, validation.
│  Controller   │  Knows nothing about SQL.
└───────┬───────┘
        ▼
┌───────────────┐  Business rules: "email must be unique", "publish an event after create".
│   Service     │  Knows nothing about HTTP or SQL syntax.
└───┬───────┬───┘
    ▼       ▼
┌────────┐ ┌──────────────┐
│ Repo   │ │ Kafka        │  Repository: talks to the database (via Hibernate).
│        │ │ Producer     │  Producer: talks to Kafka.
└────────┘ └──────────────┘
```

**Why bother?** Separation of concerns. You could swap REST for GraphQL (change only the
controller), or PostgreSQL for MySQL (change only config), without touching business rules.
It also makes each layer easy to test on its own.

### Dependency injection (how layers get connected)

No class does `new StudentService(...)`. Instead, each class **asks** for what it needs in its
constructor:

```java
public StudentController(StudentService service) { ... }
public StudentService(StudentRepository repository, StudentEventProducer producer) { ... }
```

At startup Spring creates one object ("bean") of each class and passes them in. This is
**constructor injection**. Benefits: dependencies are obvious, fields can be `final`, and in
a unit test you can pass in fakes.

## 4. What happens at startup

When you run `mvn spring-boot:run`:

1. **`main()`** in `StudentRegistryApplication` calls `SpringApplication.run(...)`.
2. **Component scan**: Spring scans `com.example.studentregistry` and sub-packages, finds every
   class marked `@RestController`, `@Service`, `@Component`, `@Configuration`, and the
   `StudentRepository` interface.
3. **Auto-configuration**: because certain libraries are on the classpath, Spring Boot sets
   them up for you:
   - `spring-boot-starter-web` → starts **Tomcat** on port 8080, sets up JSON (Jackson).
   - `spring-boot-starter-data-jpa` + PostgreSQL driver → creates a **connection pool**
     (HikariCP) to `studentdb` and starts **Hibernate**.
   - `spring-kafka` → creates a **KafkaTemplate** (producer) and a listener container (consumer).
4. **Hibernate builds the table**: `ddl-auto: update` makes Hibernate compare the `Student`
   class with the database. On the very first run you see:
   ```sql
   create table students (id bigint generated by default as identity,
       course varchar(255), email varchar(255) not null, name varchar(255) not null,
       primary key (id))
   alter table if exists students add constraint UK... unique (email)
   ```
5. **Kafka topic**: the `NewTopic` bean in `KafkaConfig` makes Spring create the
   `student-events` topic if it is missing.
6. **Spring Data** generates a class that implements `StudentRepository`.
7. **The consumer starts**: `@KafkaListener` starts a background thread that polls the topic.
8. Log line: `Started StudentRegistryApplication in ~4 seconds`. The API is ready.

## 5. Request flows, step by step

The SQL shown below is copied from the real application log (`show-sql: true`).

### 5.1 POST /api/students (create)

```
Client                Controller            Service                 Repository/Hibernate     PostgreSQL     Kafka
  │ POST JSON             │                    │                           │                    │            │
  │──────────────────────►│                    │                           │                    │            │
  │                       │ 1. JSON → Student  │                           │                    │            │
  │                       │ 2. @Valid checks   │                           │                    │            │
  │                       │───create()────────►│                           │                    │            │
  │                       │                    │ 3. existsByEmail()───────►│ SELECT ... email=? │            │
  │                       │                    │◄──────false───────────────│◄───────────────────│            │
  │                       │                    │ 4. save()────────────────►│ INSERT ... RETURNING id         │
  │                       │                    │◄──Student(id=1)───────────│◄───────────────────│            │
  │                       │                    │ 5. producer.publish() ─────────────────────────────────────►│
  │                       │◄───Student─────────│ 6. COMMIT                 │                    │            │
  │◄──201 + JSON──────────│                    │                           │                    │            │
  │                       │                    │                                    (later) consumer logs it │
```

1. **Tomcat receives the request** and Spring routes `POST /api/students` to
   `StudentController.create()`.
2. **`@RequestBody`**: Jackson turns the JSON body into a `Student` object.
3. **`@Valid`**: the `@NotBlank` and `@Email` rules on `Student` are checked. If one fails,
   the method never runs. Spring returns **400 Bad Request**.
4. **`StudentService.create()`** (runs inside a transaction because of `@Transactional`):
   - `repository.existsByEmail(email)` →
     `select s1_0.id from students s1_0 where s1_0.email=? fetch first ? rows only`
     If true → throw `ResponseStatusException(CONFLICT)` → **409 Conflict**.
   - `student.setId(null)`, so a client cannot choose or overwrite an id.
   - `repository.save(student)` →
     `insert into students (course,email,name) values (?,?,?) returning id`
     PostgreSQL generates the id; Hibernate puts it into the object.
   - `producer.publish(new StudentEvent("STUDENT_CREATED", ...))` sends JSON to Kafka.
5. The method ends, the transaction **commits**, the controller returns the `Student`.
6. `@ResponseStatus(CREATED)` → **201 Created**, and Jackson turns the object back into JSON:
   ```json
   {"id":1,"name":"Asha Rao","email":"asha@example.com","course":"Computer Science"}
   ```
7. **Asynchronously**, a moment later, the consumer thread receives the message and logs
   `Received event (pretend we send a welcome email): {...}`. The API did **not** wait for this.

### 5.2 GET /api/students and GET /api/students/{id}

- `getAll()` → `service.findAll()` → `repository.findAll()` →
  `select s1_0.id,s1_0.course,s1_0.email,s1_0.name from students s1_0`
- `getOne(id)` → `service.findById(id)` →
  `select ... from students s1_0 where s1_0.id=?`
  `findById` returns an `Optional<Student>`. `.orElseThrow(...)` turns "empty" into
  **404 Not Found** with the message `Student 999 not found`.

### 5.3 PUT /api/students/{id} (update with *dirty checking*)

```java
@Transactional
public Student update(Long id, Student input) {
    Student existing = findById(id);        // SELECT ... where id=?
    ... email-unique check ...
    existing.setName(input.getName());     // just change the Java object
    existing.setEmail(input.getEmail());
    existing.setCourse(input.getCourse());
    return existing;                        // no save() call!
}
```

**There is no `save()` call, yet the database is updated.** Why?

1. Inside a transaction, the entity loaded by `findById` is **managed** by Hibernate.
2. Hibernate keeps a snapshot of its original values.
3. When the method ends, the transaction commits. Hibernate compares the object with the
   snapshot ("is it dirty?") and generates:
   `update students set course=?,email=?,name=? where id=?`

This is called **dirty checking**. If you change the email to one that belongs to another
student, the service returns **409 Conflict**.

### 5.4 DELETE /api/students/{id}

`repository.delete(findById(id))`: first a `SELECT` (404 if missing), then
`delete from students where id=?`. The controller returns **204 No Content** (success, empty body).

### 5.5 How errors become HTTP responses

| Situation                 | Where it is detected            | Response          |
|---------------------------|---------------------------------|-------------------|
| Missing name / bad email  | `@Valid` in controller          | 400 Bad Request   |
| Id does not exist         | `findById` → `orElseThrow`      | 404 Not Found     |
| Email already used        | `existsByEmail` in service      | 409 Conflict      |

`ResponseStatusException` is a Spring exception that carries an HTTP status. Spring Boot
catches it and writes a JSON error body:

```json
{"timestamp":"...","status":409,"error":"Conflict","message":"Email already registered","path":"/api/students"}
```

(`server.error.include-message: always` in `application.yml` makes the `message` appear.)

## 6. How Kafka fits in

### Why use Kafka at all?

Without Kafka, `create()` would have to call `emailService.sendWelcome()` directly. Then:
- the API is slow if sending email is slow;
- if the email service is down, creating a student fails.

With Kafka, the service only **drops a message into a topic** and returns. Whoever is
interested reads it later. This is **decoupling**: the producer doesn't know or care who consumes.

### Key concepts, mapped to this project

| Concept            | Meaning                                             | In this project                         |
|--------------------|-----------------------------------------------------|-----------------------------------------|
| **Broker**         | A Kafka server                                      | The `kafka` Docker container            |
| **Topic**          | A named, append-only log of messages                | `student-events`                        |
| **Partition**      | A topic is split into partitions for parallelism    | 1 partition (enough for learning)       |
| **Offset**         | A message's position number in a partition          | 0, 1, 2, ... one per student created    |
| **Key**            | Decides which partition a message goes to           | The student id                          |
| **Producer**       | Writes messages                                     | `StudentEventProducer` (`KafkaTemplate`)|
| **Consumer**       | Reads messages                                      | `StudentEventConsumer` (`@KafkaListener`)|
| **Consumer group** | Consumers sharing work; each message handled once per group | `student-registry-group`        |
| **KRaft**          | Kafka manages its own metadata (no ZooKeeper)       | `KAFKA_PROCESS_ROLES: broker,controller`|

### The message flow

```
StudentService.create()
   └─► StudentEventProducer.publish(event)
         ├─ ObjectMapper: StudentEvent record → JSON string
         └─ kafkaTemplate.send("student-events", key="1", value=json)
                           │
                           ▼
                Kafka topic "student-events", partition 0, offset N
                           │
                           ▼   (background thread, polls continuously)
StudentEventConsumer.consume(String message)
   └─► log.info("Received event ...")
```

### Why the key is the student id

Kafka guarantees order **only within a partition**. Messages with the same key always go to
the same partition, so all events for student 1 (created, updated, ...) arrive in order.

### Why two Kafka ports (9092 and 29092)?

Kafka tells clients "reconnect to me at address X" (the *advertised listener*). Inside Docker
that address must be `kafka:9092`, and from your PC it must be `localhost:29092`, so we define
one listener for each:

- `EXTERNAL://localhost:29092` → used **now** by the app running on your PC.
- `PLAINTEXT://kafka:9092` → will be used in Stage 2 when the app runs inside Docker.

### A known limitation (good interview point)

The database save and the Kafka send are two separate systems. If the INSERT succeeds but
Kafka is down, the event is lost (the **dual-write problem**). Production fix: the
**Transactional Outbox pattern** (write the event to an `outbox` table in the same DB
transaction, and have a separate process forward it to Kafka).

## 7. How Hibernate fits in

```
Your code           Spring Data JPA           Hibernate (JPA impl.)       JDBC driver        PostgreSQL
repository.save() ─► SimpleJpaRepository ───► EntityManager.persist() ──► PreparedStatement ─► INSERT
```

- **JPA** is the *specification* (annotations like `@Entity` and interfaces like `EntityManager`).
- **Hibernate** is the *implementation* that actually generates and runs SQL.
- **Spring Data JPA** sits on top and writes repository classes for you
  (`JpaRepository`, derived queries like `existsByEmail`).
- **JDBC** is the low-level Java API that sends SQL to the database; the PostgreSQL driver
  implements it.

### Annotations on `Student`

| Annotation                                   | Meaning                                         |
|----------------------------------------------|-------------------------------------------------|
| `@Entity`                                    | This class maps to a table                      |
| `@Table(name = "students")`                  | Table name (default would be `student`)         |
| `@Id`                                        | Primary key                                     |
| `@GeneratedValue(strategy = IDENTITY)`       | DB generates the id (identity column)           |
| `@Column(nullable = false, unique = true)`   | `NOT NULL` and `UNIQUE` constraints in the DDL  |
| `@NotBlank`, `@Email`                        | Validation rules (checked by `@Valid`, not DB)  |

Hibernate requires a **no-args constructor** because it creates the object first and then
fills in the fields from the result set.

### `@Transactional`

Wraps the method in a database transaction: `BEGIN` before, `COMMIT` after, or `ROLLBACK`
if a runtime exception is thrown. It is also what makes dirty checking work (section 5.3).

## 9. Configuration explained

`src/main/resources/application.yml`:

| Setting                               | Value                                        | Why                                              |
|---------------------------------------|----------------------------------------------|--------------------------------------------------|
| `spring.datasource.url`               | `jdbc:postgresql://localhost:5432/studentdb` | Where the database is                            |
| `spring.datasource.username/password` | `student` / `student123`                     | DB login (created during setup)                  |
| `spring.jpa.hibernate.ddl-auto`       | `update`                                     | Hibernate creates/alters the table. **Not for production**; use Flyway/Liquibase there |
| `spring.jpa.show-sql`                 | `true`                                       | Print SQL so you can see Hibernate working       |
| `spring.jpa.open-in-view`             | `false`                                      | Close DB session when the service ends (avoids hidden lazy-loading queries in the controller) |
| `spring.kafka.bootstrap-servers`      | `localhost:29092`                            | Kafka's external port                            |
| `spring.kafka.consumer.group-id`      | `student-registry-group`                     | Consumer group name                              |
| `spring.kafka.consumer.auto-offset-reset` | `earliest`                               | A new group starts reading from the oldest message |
| `server.port`                         | `8080`                                       | HTTP port                                        |
| `server.error.include-message`        | `always`                                     | Include our error text in error JSON             |

**Overriding with environment variables (used in Stage 2):** Spring maps
`SPRING_DATASOURCE_URL` → `spring.datasource.url` automatically (upper-case, `.` → `_`).
The same JAR can run anywhere; only the environment changes.

## 10. Setup and run (Windows)

### Prerequisites (already on this PC)

| Tool            | Version used | Check with           |
|-----------------|--------------|----------------------|
| Java JDK        | 21 (project targets 17) | `java -version` |
| Maven           | 3.9          | `mvn -version`       |
| PostgreSQL      | 18           | Windows service running on 5432 |
| Docker Desktop  | 29           | `docker info`        |

### One-time: create the database user and database

Already done for you. To redo it on another machine, open **SQL Shell (psql)** or run:

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -h localhost
```
```sql
CREATE USER student WITH PASSWORD 'student123';
CREATE DATABASE studentdb OWNER student;
```

You don't create the table yourself: Hibernate does it on first startup.

### Every time: start the app

Open a terminal in the `student-registry` folder.

**Step 1: start Docker Desktop** (wait until it shows "Engine running").

**Step 2: start Kafka**
```powershell
docker compose up -d
docker compose ps          # STATUS should become "healthy" after ~20 seconds
```

**Step 3: start the app**
```powershell
mvn spring-boot:run
```
Wait for: `Started StudentRegistryApplication in ... seconds`.

(Alternative: build a JAR and run it.)
```powershell
mvn package -DskipTests
java -jar target\student-registry-0.0.1-SNAPSHOT.jar
```

**Stop:** `Ctrl + C` stops the app. `docker compose down` stops Kafka.

## 12. Troubleshooting

| Symptom                                                        | Likely cause                         | Fix |
|----------------------------------------------------------------|--------------------------------------|-----|
| `password authentication failed for user "student"`            | User/DB not created                  | Run the SQL in section 10 |
| `Connection to localhost:5432 refused`                          | PostgreSQL service stopped           | Windows → Services → start `postgresql-x64-18` |
| App log repeats `Connection to node -1 ... could not be established` | Kafka not running               | Start Docker Desktop, `docker compose up -d` |
| POST hangs ~60 s then fails                                    | Kafka down; producer waits for it    | Same as above |
| `failed to connect to the docker API`                          | Docker Desktop not started           | Start Docker Desktop and wait for "Engine running" |
| `Port 8080 was already in use`                                 | Another app (or old run) on 8080     | Stop it, or set `server.port: 8081` |
| `409 Conflict` on POST                                         | Email already exists                 | Expected; use a different email |

## 13. What comes next

**Stage 2: Docker.** Add a `Dockerfile` (multi-stage: Maven builds the JAR, a small JRE image
runs it) and add `postgres` and `app` services to `docker-compose.yml`. The app container
will reach `postgres:5432` and `kafka:9092` by service name, set via environment variables.
(Note: your local PostgreSQL already uses port 5432, so the Postgres container will be
mapped to a different host port, e.g. `5433:5432`.)

**Stage 3: AWS EC2.** Run the same `docker compose up` on an Ubuntu EC2 instance, opening
only ports 22 (SSH) and 8080 (API) in the Security Group.
